## 05 KV Cache

**Q：什么是 KV Cache？为什么需要？有什么优化方法？**

**参考答案：**

**KV Cache：** 在自回归生成中，已生成 token 的 K 和 V 可以缓存复用，避免重复计算。

**生成第 t 个 token 时：**
- 无 Cache: 计算 t 次 attention，复杂度 O(t²)
- 有 Cache: 只需计算第 t 个 Q，与缓存的 K/V 做 attention，复杂度 O(t)

**问题：** KV Cache 随序列增长，显存占用大
- LLaMA-7B, batch=1, seq=2048 → ~2GB KV Cache
- LLaMA-70B, batch=8, seq=4096 → ~80GB

**优化方法：**

| 方法 | 原理 | 效果 |
| :--- | :--- | :--- |
| PagedAttention | 分页管理 KV Cache | 减少碎片 |
| Quantization | KV 量化为 8/4-bit | 2-4x 压缩 |
| Eviction | 淘汰不重要的 KV | 减少长度 |
| GQA/MQA | 共享 KV 头 | 减少参数 |

## 06 PagedAttention

**Q：PagedAttention / vLLM 的核心原理是什么？**

**参考答案：**

**问题：** 传统 KV Cache 连续分配，导致内存碎片化和浪费（特别是 beam search / 并发请求时）。

**PagedAttention（借鉴 OS 虚拟内存）：**
1. 将 KV Cache 分成固定大小的 block（如每 block 存 16 个 token 的 KV）
2. 用 block table 记录逻辑→物理映射
3. 按需分配 block，不需要连续内存

**vLLM 系统优势：**
| 方面 | 传统 serving | vLLM |
| :--- | :--- | :--- |
| 内存利用率 | 20-40% | ~95% |
| 吞吐量 | baseline | 2-4x |
| 并发 | 受限于显存 | 更高并发 |
| Continuous Batching | 不支持 | 支持 |

**Continuous Batching：**
不同于 static batching（等所有请求完成才开下一批），continuous batching 在每步检查是否有请求完成，完成的立刻移出，新请求立刻加入，最大化 GPU 利用率。

**延伸思考：**
- Continuous Batching 和 Static Batching 的吞吐量差多少？
- 如果序列长度差异很大，continuous batching 的优势有多大？
